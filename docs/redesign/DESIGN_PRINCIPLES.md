# 設計原則：擺脫 AI 味，做出真人資深設計師水準的介面

> 本文件為 FRC 報帳/庫存/資金管理系統重新設計的核心參考，供後續「定義設計系統」「全頁面重設計」「視覺驗證」等階段直接引用、逐項核對。
> 適用範圍：Next.js + Tailwind CSS，繁體中文介面，使用者為高中生隊員與指導老師。
> 更新日期：2026-07-03

## 這份文件在解決什麼問題

AI 生成介面之所以一眼就能被認出來，根本原因不是「AI 品味差」，而是統計上的收斂：語言模型被要求「做一個看起來現代的介面」時，會傾向輸出訓練資料中出現頻率最高、最不會出錯的答案——Inter 字體、indigo/purple 漸層、`rounded-2xl shadow-lg` 卡片。這些選擇沒有一個是「錯的」，錯在所有人都拿到同一組「最安全的平均值」，於是所有 AI 產出的介面都長得像兄弟姊妹。

真人資深設計師做出來的介面之所以不會撞臉，是因為每個視覺決定都回應了具體脈絡（這個產品、這群使用者、這個場景），而不是套用一個可以放諸四海皆準的風格濾鏡。

本文件分四部分：

- **A. AI 味特徵黑名單**——審計現有頁面、審查新元件時的檢查清單，每條說明「為什麼看起來像 AI」。
- **B. 人味設計原則**——具體可直接照做的正向做法，對應 A 部分的問題。
- **C. 本專案適用建議**——針對這個財務/庫存工具 + 高中機器人隊伍脈絡，提出三個方向並推薦其一。
- **D. 繁中字型技術方案**——在 CSP `font-src 'self'` 限制下，如何正確自託管繁體中文字型。

文中標註「**本專案現況**」的段落，是實際讀取 `app/globals.css`、`app/layout.tsx`、`next.config.mjs` 後對照到的具體例子，方便直接定位要處理的程式碼位置。本次研究只讀取程式碼作為佐證，未修改任何檔案。

## A. AI 味特徵黑名單

共 27 條，依主題分組，可作為程式碼審查/視覺驗收的逐項核對清單。

### 色彩

**A1. Indigo/violet 到 blue/purple 的漸層背景或按鈕**
（`bg-gradient-to-r from-indigo-500 via-purple-500 to-blue-500` 這類漸層）
為什麼像 AI：Tailwind 官方範例多年來大量用 `indigo-500`/`purple-600` 示範「現代感」，訓練資料中這類配色密度極高，模型在沒有明確指示時會收斂到這個「統計上最安全」的選擇——不是因為紫色特別好看，而是因為它是訓練分布的中心值。

**A2. 漸層文字標題（`background-clip: text` + `text-transparent`）**
為什麼像 AI：犧牲可讀性換取「看起來很精緻」的裝飾效果，是 AI 工具讓標題「看起來更講究」的慣用手法，且會拖累掃描性（眼睛必須更用力才能辨識文字邊界）。
**本專案現況**：`app/globals.css:612-618` 目前把**所有** `h1` 都強制套用漸層文字效果，不分頁面情境（登入頁標題和報帳表單標題視覺處理完全相同）。

**A3. 到處都是彩色光暈陰影（colored glow box-shadow）**
為什麼像 AI：模型把「科技感」等同於「發光」，於是把 `box-shadow: 0 0 20px rgba(...)` 套在按鈕、卡片、輸入框、數字上，不分場合,變成視覺噪音而非有意義的強調。
**本專案現況**：`.bg-primary`、`.card`、`.bento-card`、`.tech-number`，以及**所有** `text-2xl`/`text-3xl` 元素（`app/globals.css:583-587`）都各自疊加藍色光暈——後者尤其值得注意，因為它是依「字級大小」這個跟語意無關的條件觸發，任何剛好用到這兩個字級的文字（不論是不是金額）都會被套上發光效果。

**A4. 永久深色模式 + 對比不足的中灰內文**
為什麼像 AI：研究顯示「永久深色主題」是目前單一出現率最高的 AI 產出特徵（約 34% 的頁面），常伴隨未達 WCAG AA 對比標準的灰階內文——模型模仿「看起來高級」的視覺樣本，但沒有真的檢查對比度數字。

**A5. 呼吸燈式的邊框/陰影脈動動畫套用在靜態元件上**
為什麼像 AI：無限循環的 `glow-pulse`、`border-glow` 動畫常被套在不需要持續吸引注意力的元件上，製造「看起來很科技」的錯覺,但對任務沒有幫助，長時間使用反而分心。
**本專案現況**：`app/globals.css:589-609` 的狀態指示燈固定套用 `glow-pulse`，不論該狀態是否需要使用者立即注意（「已核准」跟「待審核」用同一種脈動強度）。

**A6. 紫色系裝飾元素即使主題主色不是紫色也會滲入**
為什麼像 AI：紫色（尤其 `#a855f7`/`purple-500` 一帶）在訓練資料中被過度關聯到「AI/魔法/特效」語意，即使整體配色是藍色系，裝飾性的粒子、星星、sparkle 效果仍常「自動」變成紫色。
**本專案現況**：`app/globals.css:734-741` 的粒子閃爍動畫使用 `rgba(168, 85, 247, ...)`（即 Tailwind `purple-500`），即使本專案主色調整體是藍/青（`hsl(199 89% 48%)` 起）——這正是「AI 紫」滲入非紫色主題的具體案例。

### 字體

**A7. 只用 Inter/Roboto/system-ui 作為唯一字體，沒有任何字體個性**
為什麼像 AI：Inter 是 Google Fonts 與各元件庫（含 shadcn/ui、Linear）的預設字體，訓練資料中「看起來乾淨專業」的介面幾乎都用它，模型把它學成了「正確答案」。
**本專案現況**：`app/layout.tsx:12` 目前唯一透過 `next/font/google` 載入的字體就是 `Inter`（詳見 Part D）。

**A8. 標題全大寫 + 拉寬字距（uppercase tracking-widest）**
為什麼像 AI：這是行銷落地頁的樣板手法，被大量複製進 AI 生成的元件範例，套用在任何「想要看起來正式」的標籤或章節標題上——對中文標題完全無效（中文沒有大小寫），卻常被誤用在英文按鈕字或狀態標籤上。

**A9. 用襯線斜體字強調單一英文字**
為什麼像 AI：近期 AI 落地頁生成器很愛用的花招——在無襯線內文中插入一個斜體襯線字（例如 "Build *better*"）製造「有設計感」的錯覺，實際上只是隨機挑一個字加花體，跟語意無關。

**A10. 扁平字級階層（標題和內文大小差距過小、字重差距過小）**
為什麼像 AI：模型傾向輸出「安全」的中間值，`text-lg` 和 `text-xl` 滿天飛,卻很少出現真正大膽的大小對比，結果是介面「看起來都差不多重要」，沒有清楚的視覺入口。

### 卡片與陰影

**A11. 每張卡片都是 `rounded-2xl shadow-lg` + hover 位移放大**
為什麼像 AI：這是 shadcn/ui 的預設卡片樣式，設計初衷就是給開發者「複製貼上堪用」，AI 代理最常見的行為就是原封不動採用這個預設,結果是所有 AI 生成產品的「卡片」長一個樣。

**A12. 玻璃態（glassmorphism）到處使用：`backdrop-blur` + 半透明背景/邊框**
為什麼像 AI：2022 年起流行的視覺效果，因為在教學文章與元件庫範例中出現頻率極高，變成模型「讓介面看起來現代」的預設手段之一，但在資訊密集的工具（財務、庫存）中會犧牲對比度和可讀性。
**本專案現況**：`app/globals.css` 中 `.card`、`.bento-card`、`.header-glass`、`.glass` 皆使用 `backdrop-filter: blur(...)`，深淺色主題都套用同一套處理，屬於不分場景的全域反射動作，而非針對特定情境的刻意選擇。

**A13. 卡片內還有卡片（巢狀卡片造成視覺噪音）**
為什麼像 AI：每個資訊區塊都被「包一層卡片」是最保守、最不需要思考版面關係的做法，模型傾向對任何內容分組都套用同一個容器樣式,而不是判斷這組內容是否真的需要獨立的邊框/陰影/背景色。

**A14. 圖示放在彩色圓角方塊裡置頂於卡片（icon-in-box 功能卡樣板）**
為什麼像 AI：這是行銷網站「三欄功能介紹」的公式化樣板，被大量複製進元件生成範例，變成模型描述任何「一組項目」時的預設呈現方式，即使內容其實是資料而非行銷賣點。

**A15. 全站唯一一個誇張圓角值，不分元件大小地套用**
為什麼像 AI：模型抓住一個「看起來柔和現代」的圓角數值（常見 16-24px）就整站套用，從按鈕、輸入框到整個頁面容器都用一樣的弧度，沒有依元件實際尺寸做比例調整——大容器和小按鈕用同一個圓角，比例上會顯得失衡。

### 圖示與插圖

**A16. 用 emoji 取代正式圖示系統**
為什麼像 AI：emoji 是最低成本的「圖示」——不用挑圖示庫、不用處理 SVG，模型直接輸出文字字元即可完成任務，但 emoji 在不同作業系統/瀏覽器渲染完全不同，也無法跟隨介面的 stroke-width、色彩、尺寸系統統一,專業工具中會顯得業餘。

**A17. 過度使用 ✨ sparkles 符號象徵「AI/智慧」**
為什麼像 AI：sparkles 圖示已經變成 AI 產品的視覺代名詞，AI 生成介面在描述任何「智慧」「自動」相關功能時,高機率自動加上 ✨,變成一種可預測、廉價的視覺速記,而非真正為產品設計的圖示語言。

### 版面

**A18. 置中英雄區公式：徽章 + 大標題 + 副標 + 兩顆 CTA 按鈕**
為什麼像 AI：這是 SaaS 行銷落地頁近十年的標準公式，訓練資料密度極高，模型對「首頁應該長什麼樣」的預設答案幾乎唯一。這個公式對行銷頁或許合理，但套用在登入後的工作台首頁（例如報帳系統的儀表板）完全文不對題——使用者要的是「我現在有幾筆待審核」，不是行銷標語。

**A19. 三欄或四欄同尺寸功能卡片網格**
為什麼像 AI：模型描述「一組東西」的預設佈局就是等寬網格卡片，不管內容彼此的重要性、資料量、互動需求是否相同，導致所有項目視覺權重一致，使用者無法一眼判斷哪個更重要。

**A20. 置中的大數字+小標籤統計橫幅**
為什麼像 AI：「大數字、小說明文字、三個並排」是行銷頁展示「成果」的公式化排法。在真正的儀表板情境裡，統計數字通常需要跟其來源資料（例如可點擊查看明細的列表）放在一起,而不是抽離成裝飾性的展示區塊。

**A21. 內容緊貼視口邊緣，或反過來把工作區內容過度置中**
為什麼像 AI：模型對「留白」只有兩種預設——完全不留（`p-2` 到底）或整頁置中再限制一個 `max-w-xl` 塞在螢幕正中央——這兩種都是取巧、無需判斷內容結構的做法，缺乏因應真實資料量與螢幕尺寸的版面決策。

### 動效

**A22. 彈跳/彈性緩動（bounce/elastic easing）套用在一般 UI 過場**
為什麼像 AI：這種緩動函數在 CSS 動畫教學與套件中作為「有趣」的示範大量出現，模型將其視為「有動感」的預設選擇，但在工作型介面中會讓每個互動都顯得輕浮、拖慢操作節奏。

**A23. 每個元件的 hover 都做同一組「放大 + 位移 + 加陰影」，沒有主次之分**
為什麼像 AI：模型沒有「這個互動值不值得被強調」的判斷力，於是把同一套微互動公式（`hover:scale-105 hover:-translate-y-1 hover:shadow-xl`）貼到所有可互動元素上，結果是使用者滑過任何東西都得到一樣強度的反饋，重要操作（刪除、送出）和次要操作（展開列）在視覺上毫無區別。

### 文案

**A24. 空泛的行銷語氣標題（「Streamline your workflow」「Empower your team」）**
為什麼像 AI：這類詞彙密度在 SaaS 行銷文案訓練樣本中極高，模型學到「這是介面標題該有的語氣」，但完全沒有具體說明使用者能做什麼；翻成中文後（「賦能您的團隊」「打造無縫體驗」）違和感更明顯，高中生使用者會覺得空洞甚至可笑。

**A25. 大量使用 em-dash 與對仗式格言文案（「不只是 X，更是 Y」）**
為什麼像 AI：這是近年大型語言模型文字輸出的已知節奏特徵，讀者一眼就能認出「這是 AI 寫的」；用在按鈕文案、空狀態提示這種使用者實際要照做的地方尤其扣分，因為它優先考慮「聽起來漂亮」而非「講清楚要做什麼」。

### 程式碼寫法

**A26. 用全域 CSS selector 依 class 名稱套樣式，而非針對 component 設計**
為什麼像 AI：模型傾向寫「看起來能一次套用到最多地方」的規則（例如 `.rounded-xl.border { ... }` 或 `input, select, textarea { ... !important }`），而不是為每個 component 精確設計樣式。這種寫法短期內「看起來統一」，但把視覺效果耦合到一組恰好符合的 class 組合上，未來任何人只要寫出同樣的 class 組合就會意外繼承這個「特效」，難以預期、難以覆寫。
**本專案現況**：`app/globals.css:137-138`（`.card, .rounded-xl.border` 自動套用科技卡片效果）與 `:161-176`（`input, select, textarea` 用 `!important` 強制覆寫）都屬於這個模式——任何新元件只要用到 `rounded-xl border` 這組 class，即使原意只是想要一個普通邊框方塊，也會被迫繼承漸層背景、光暈陰影跟 hover 位移。

**A27. 每個元件各自重新發明陰影/圓角/間距數值，而非引用設計 token**
為什麼像 AI：模型沒有「記住」前面幾個元件用過哪些數值的機制（除非明確給它一份 token 清單），於是新增的每個 class 都各自寫一組相近但不完全相同的陰影/圓角/間距（例如同一個檔案裡出現 `0 4px 30px rgba(0,0,0,0.3)`、`0 8px 40px rgba(0,0,0,0.4)`、`0 2px 12px rgba(0,0,0,0.15)` 這種細微不同的變體）。結果是介面「感覺」風格統一（因為都很浮誇），但實際數值毫無系統，之後要調整或做深色/淺色主題切換時,每一處都要手動比對修改。

## B. 人味設計原則

共 20 條，每條都具體到可以直接照做，對應 Part A 指出的問題。

### 色彩與對比

**B1. 一個強調色，嚴格用在「使用者該採取行動」的地方**
用 60/30/10 分配：60% 主要背景/介面色，30% 次要結構色（卡片、側邊欄底色），只留 10% 給單一強調色，而且這個強調色只出現在主要按鈕、連結、當前選中的導覽項目、和真正需要被注意的警示上。不要把強調色用在裝飾性邊框、圖示背景、hover 光暈這些地方——強調色出現的地方越少，真正出現時才越有意義（對照 A1、A3、A6）。

**B2. 深色模式不要靠陰影做立體感，靠表面色階**
定義 3-4 階遞增亮度的表面色（`surface-0` 背景 → `surface-1` 卡片 → `surface-2` 彈出層 → `surface-3` 懸浮選單），層次靠「越上層越亮」+ 1px 邊框區分。陰影在深色背景上幾乎看不見，硬加只會增加 CSS 複雜度卻沒有實際視覺效果。

**B3. 負數/警示狀態不能只靠顏色**
金額為負時，除了變色（紅），也要加上第二個視覺線索——前綴減號、括號（會計慣例，例如 `(1,200)`）、或圖示，讓色盲使用者與黑白列印都能判讀。狀態同理：不要只用色塊區分「已核准/待審核/已退回」，一定搭配文字或圖示（呼應 B8）。

### 邊框與深度

**B4. 用 1px 實體邊框分隔區塊，陰影只留給真正「浮起」的元素**
卡片、表格、側邊欄之間的分隔預設用 `border` 而非 `shadow`；陰影保留給 dropdown、modal、tooltip 這種真的疊在其他內容「之上」的元素，且一次只疊一層陰影，不要邊框、陰影、彩色光暈三個一起上（對照 A3、A12）。

**B5. 圓角只分兩級**
訂一個小圓角（例如 4-6px）給互動元件（按鈕、輸入框、checkbox），一個大圓角（例如 8-12px）給容器（卡片、modal、面板），全站只用這兩個值。Ramp 的做法是嚴格二階系統（4px 功能元件、12px 卡片/面板），效果簡潔一致，可作為參考基準（對照 A15）。

**B6. 對齊到 4px 網格**
所有 padding/margin/gap 只用 4 的倍數（4/8/12/16/24/32...），不要出現 13px、22px 這種隨意數值；Tailwind 預設間距尺度已經是這個邏輯，只要不手動寫 arbitrary value 就能維持一致。少數需要「視覺置中」的例外（例如圖示因自身留白造成視覺不居中）才手動微調 1-2px，且留註解說明原因。

### 數字與資料呈現

**B7. 金額與所有表格數字一律 `tabular-nums` + 右對齊**
```css
.tnum {
  font-variant-numeric: tabular-nums;
}
```
套用在所有金額、數量、日期的數字欄位，並靠右對齊，讓小數點/千分位對齊成列，一眼能比較大小。這是資料密集的財務/庫存介面的最低標準,不是可選項（對照 A3 的 `.tech-number` 目前只做了 tabular-nums 但又疊加了發光陰影，數字本身的對齊已經做對，只需拿掉裝飾）。

**B8. 狀態用「小圓點 + 文字」，不要用大色塊藥丸**
一個 6-8px 的實心圓點加上清楚的文字標籤（例如 `● 待審核`），而不是整塊高飽和度背景色的膠囊徽章。圓點小、剋制，文字負責傳達語意，掃視一整欄狀態時不會像紅綠燈一樣刺眼。本專案目前的 `.status-indicator` 已經是圓點形式（`app/globals.css:589-595`），只需要拿掉不分場合的 `glow-pulse` 動畫。

**B9. 大數字加千分位，超過門檻可選擇「萬」為單位並清楚標示**
新台幣金額一律加千分位逗號（`123,456`）；若介面需要顯示總覽層級的大數字（例如年度預算總額），可提供「以萬元為單位」的顯示選項，但必須在旁邊清楚標示單位文字（「萬元」），不要只縮寫數字卻不註明，以免與明細頁的「元」搞混。

**B10. 表格用清楚的欄位分隔，斑馬紋和邊框擇一，不要疊加**
資料表格選一種列分隔方式（列與列之間的 1px 底線，或交替的斑馬紋背景），不要兩個同時上，也不要再疊加陰影或漸層表頭。表頭用比內容略深的背景色或較粗字重來區隔即可，不需要漸層（對照本專案 `thead` 目前的漸層背景，`app/globals.css:179-184`）。

### 密度與留白

**B11. 資訊密度優先於留白**
財務/庫存系統的使用者是要處理大量資料的「熟手」（隊員、老師），不是被行銷頁吸引來的訪客。表格列高抓 36-40px（`py-2` 上下）而非行銷頁常見的 `py-4` 以上，讓一個螢幕能看到更多筆資料；細節與次要操作可以透過 hover/點擊展開，不需要預設就攤開佔滿留白。

**B12. 工作區內容一律左對齊起排，置中只留給行銷/空狀態頁**
表單、表格、清單一律靠左對齊、頂寬顯示（不要塞進一個置中的 `max-w-xl` 容器裡飄在畫面正中央）；只有登入頁、404、真正的「空狀態」插畫這類非工作型頁面才適合置中構圖（對照 A18、A21）。

### 圖示與狀態回饋

**B13. 圖示統一用單一圖示庫，不與 emoji 混用**
整站只用一套圖示庫（例如 lucide-react），統一 stroke-width（通常 1.5-2px）與尺寸（16/20/24px 三檔對應不同情境），圖示只作為文字的輔助，不單獨承載語意；不要用 emoji 取代圖示，也不要把圖示塞進額外的彩色圓角方塊裡當裝飾（對照 A14、A16、A17）。

**B14. 重要操作要有具體、剋制的回饋文字**
完成寫入/刪除等操作後，用 toast 或行內訊息明確描述「做了什麼」（例如「已核准 3 筆報帳單」而非「操作成功」），不需要誇張的慶祝動畫或音效；空狀態文字要講清楚下一步（例如「尚無報帳紀錄，點擊右上角新增第一筆」而非只放一張插圖加「目前沒有資料」）。

### 動效

**B15. 一頁只給一個動效重點，其餘互動用簡單的 150-200ms transition**
頁面載入時可以有一次性的、有次序的內容浮現（stagger reveal），這是值得投資的「亮點時刻」；除此之外，一般的 hover/focus/選中狀態只做顏色或透明度的簡單過渡，不要每個可互動元素都做「放大+位移+加陰影」三件套，避免使用者操作時畫面到處在跳動（對照 A5、A22、A23）。
**本專案現況**：目前有一組相當講究的頁面切換「豹爪撕裂」動畫效果（`app/globals.css:632-741`），屬於這類值得投資的亮點時刻之一，技術上做得不差；可以評估保留在真正需要儀式感的場景（例如登入、切換組織），但不需要擴散成每次路由切換都播放——日常的表單送出、篩選切換這類高頻操作應該追求「快」而非「炫」，過場動畫的時間成本會直接疊加在使用者每天重複的操作上。

### 文案

**B16. 按鈕與提示文字講人話、講具體動作**
按鈕文字直接寫使用者會做的事（「送出報帳單」「核准」「退回並填寫原因」），不要用「立即開始」「了解更多」這種空泛詞彙；錯誤訊息要講清楚錯在哪、怎麼修正（「金額不能為 0」而非「發生錯誤」）（對照 A24、A25）。

### 字體排印

**B17. 中文字重只用 2-3 檔，避免過細字重**
內文固定用 400（Regular），強調/次標題用 500，主標題用 700；不要使用 300 以下的字重——Windows 對細字重中文字的渲染常會模糊，尤其在 14px 以下的表格文字上更明顯。

**B18. 行高依內容密度分級**
一般中文內文行高抓 1.6-1.8（易讀性優先）；資料密集的表格內文可以縮到 1.4-1.5；標題行高收緊到 1.2-1.3 並視覺上更靠近它所屬的內容區塊，讓「標題與內容的距離」小於「這組內容與下一組內容的距離」，用距離本身傳達群組關係，不需要額外加邊框分隔每一組標題。

### 個性來源

**B19. 個性來自脈絡具體的細節，不是風格濾鏡**
與其套用抽象的「科技感發光」「玻璃質感」這種可以套用在任何產品上的風格濾鏡，不如從這個團隊真實的視覺語彙找個性——隊伍代表色、隊號、比賽相關的術語與格式（例如零件編號、賽季代號）。這些東西獨一無二、無法被隨便一個 AI 生成的「科技風」模板複製，自然就不會撞臉（詳見 Part C）。

**B20. 建立一份 token 清單並在動工前鎖定，而非邊做邊決定**
把顏色、字體、圓角、陰影、間距這些決策寫成一份簡短的 token 清單（顏色的 HSL 值、圓角的兩個尺寸、陰影只有 0-2 種、字重只有 2-3 檔），開工前定案。所有元件只能引用這份清單裡的值，不允許各自發明相近但不同的數字——這是 A26、A27 提到的問題的根本解法，也是後續「定義設計系統」階段的直接產出物。

## C. 本專案適用建議

背景：這是一個財務/庫存/資金管理系統，資料密度天生就高（報帳明細、庫存數量、資金往來），使用者是高中生隊員（送報帳單、查庫存）與指導老師/財務幹部（審核、核准）。現況（`app/globals.css`）走的是「科技感」風格濾鏡路線——深色底、藍青漸層、玻璃態、光暈——這條路線的問題不是「醜」，而是它跟內容無關：同一套「科技感發光卡片」貼在任何一個工具型 SaaS 產品上都成立，沒有反映這是「一支特定 FRC 隊伍的報帳系統」這個事實，這正是 A19 條目描述的問題在整個產品層級的放大版。

以下提出三個方向，每個都包含色彩策略、字體策略、密度策略、個性來源，最後推薦其一。

### 方向一：精確工程感（Engineering Precision）— 推薦

**色彩策略**：近乎單色的基底（石墨灰/深藍黑的深色版本，或暖白/淺灰紙感的淺色版本）+ 一個強調色取自隊伍實際代表色（隊服、隊旗、機器人塗裝上真正在用的顏色），嚴格遵守 B1 的 60/30/10——強調色只出現在主要按鈕、連結、待處理提醒上，不作裝飾用途。

**字體策略**：中文內文與介面文字用自託管 Noto Sans TC（見 Part D），只取 400/500/700 三檔；金額與一般數字直接用同一字體的 tabular-nums 特性即可，不需混搭西文字體。報帳單編號、零件編號、庫存料號這類「規格型」文字可用等寬字體（monospace）呈現，強化「這是一份可追蹤的正式紀錄」的質感，而不是隨便一串文字。

**密度策略**：高密度。表格用緊湊列高（B11），側邊欄可摺疊，桌機版以資料總覽為主；手機版（含 Capacitor iOS App）才切換為卡片式單欄呈現。財務審核者一次要看的是一整批報帳項目，不是一張一張滑的資訊卡。

**個性來源**：從 FRC 隊伍真實會接觸的視覺語彙取材，而非通用科技感——例如表格分隔線的處理方式參考規格表/BOM 表（Bill of Materials）的清楚實線分格；狀態指示用真正「指示燈」的語彙（實色圓點 + 剋制的 ring，不做無差別脈動）；單據編號採用類似零件編號的格式（例如 `EXP-2026-0143`）。這些細節高中生隊員每天在工程筆記本、CAD 軟體、零件清單裡都會看到，比套用「未來感」濾鏡更容易產生「這是我們隊伍自己的系統」的認同感。

**為什麼推薦這個方向**：
1. 天生貼合 FRC 機器人隊伍的真實脈絡——工程筆記本、CAD 圖面、零件規格是隊員每天在用的真實視覺語言，比起硬套 fintech 新創的高級感更真誠，也更不會變成「換了顏色的另一套模板」。
2. 財務+庫存系統本質是資料密集工具，工程感偏好的高密度、清楚分隔線、等寬編號恰好服務這個需求，不需要為了塞入某種美學而犧牲可用性。
3. 對「去 AI 味」特別有效：規格表、指示燈、零件編號這類視覺語彙在訓練資料裡不是 SaaS 登陸頁的高頻模式，AI 很難「拿最保守的猜測」湊出這個方向，天然不容易撞臉。
4. 高中生使用者仍會覺得「這樣做很酷」（工程感不等於無聊），同時老師/財務審核者會覺得專業可信，不會有「這是玩具」的觀感。

### 方向二：溫暖務實（Warm Practical，Notion 式）

**色彩策略**：暖白/米色背景 + 深灰文字，強調色用隊伍代表色的暖色調版本，整體降低「科技感」冷色調比例，讓高中生與老師都覺得友善不生硬。

**字體策略**：標題可用略帶個性但仍高辨識度的中黑體，內文維持 Noto Sans TC Regular，數字一樣套用 tabular-nums。

**密度策略**：中密度，保留適度留白但不像行銷頁那樣浪費空間，表格與卡片視情境並用（例如列表用表格、單筆報帳的審核詳情用卡片）。

**個性來源**：核准流程可以有「簽核感」的視覺痕跡（核准者姓名 + 時間戳的呈現方式參考紙本簽核單，但不做成擬物化插畫），強調色來自隊伍真實識別。

**取捨**：比方向一更容易上手、對非技術背景的老師更友善，但「溫暖」風格在市面上（尤其 Notion 之後）也快速變成一種新的可辨識模板，個性感比方向一弱，且容易在無意間又滑回「一般 SaaS 工具」的既視感。

### 方向三：極簡財務（Minimal Financial，Mercury / Ramp 式）

**色彩策略**：近單色 ivory/onyx 基底 + 單一鮮明強調色，嚴格雙圓角系統（4px/12px），這是目前國外新創財務工具（Mercury、Ramp）驗證有效的路線。

**字體策略**：偏幾何感的無襯線字體搭配 Noto Sans TC，大量留白但只用在區塊與區塊之間，不用在表格內部。

**密度策略**：中高密度，但版面對齊、間距節奏要求非常精確。

**個性來源**：個性不靠裝飾元素，靠「精準」本身——對齊、間距、動效節奏統一到接近工業標準的一致性，這種一致性本身會被使用者感知為「講究」。

**取捨**：視覺品質天花板最高，但執行難度也最高（容錯率低，一旦有一處間距沒對齊就會顯得廉價），且這條路線本質上是在模仿矽谷 fintech 新創的美學語言，跟「FRC 高中機器人隊伍」這個脈絡的連結最弱，比較容易變成「做得很像 Mercury，但為什麼一個學生社團要長得像矽谷新創」的違和感。

### 建議

**推薦方向一（精確工程感）**。理由已在方向一段落列出，核心是：這是唯一一個「個性來源」直接根植於使用者真實生活經驗（FRC 工程文化）而非借用外部美學語言的方向，也最符合財務/庫存工具的資料密度需求。方向二可作為「精確工程感」執行上手感不足時的降階選項（例如時程/人力有限時，先做出方向二的溫和版本，之後再往方向一的細節收斂）；方向三不建議採用，因為它解決的是「如何做出頂級 fintech 美學」，不是「如何讓這個系統看起來是我們隊伍自己的東西」。

## D. 繁中字型技術方案

### 現況

- `app/layout.tsx:12` 透過 `next/font/google` 載入 `Inter`，只指定 `subsets: ["latin"]`，**沒有載入任何中文字型**。
- `app/globals.css:88` 的 `body` 字型堆疊寫著 `var(--font-sans), "LXGW WenKai", "Noto Sans TC", sans-serif`——但 `LXGW WenKai` 與 `Noto Sans TC` 兩者在專案中都**沒有對應的 `@font-face` 或 `next/font` 設定**，代表這兩個字型名稱實際上從未被載入。目前所有中文字的實際顯示,是瀏覽器/作業系統找不到這兩個具名字型後，落到 `sans-serif` 通用字族的結果——Windows 上通常解析為微軟正黑體、Mac/iOS 上為蘋方（PingFang TC）。也就是說，現在頁面上的中文字型「看起來」是什麼,其實完全取決於使用者的作業系統，不是設計者刻意選定的結果，同一頁面在不同裝置上字重、字寬觀感都不一致。
- `next.config.mjs:15` 的 CSP 設定是 `font-src 'self' data:`，**不允許**從 `fonts.googleapis.com`/`fonts.gstatic.com` 這類外部網域直接載入字型（例如透過 `<link href="https://fonts.googleapis.com/...">` 的傳統做法會被 CSP 擋下）。

### 解法：`next/font/google` 自動自託管，天然符合現有 CSP

`next/font`（不論 `next/font/google` 或 `next/font/local`）的運作方式是在**建置時**下載字型檔並打包進 `.next/static/media`，瀏覽器執行期間完全不會對 Google 發出任何請求，字型檔跟其他靜態資源一樣是從自己的網域送出。這代表：

- 不需要放寬 `font-src` 去允許 `fonts.gstatic.com`——現有的 `font-src 'self' data:` 已經足夠，維持原樣即可。
- 用 `next/font/google` 載入 `Noto_Sans_TC` 跟用 `next/font/local` 手動放字型檔，在「是否自託管」這件事上結果相同，前者由 Next.js 自動處理下載與最佳化，更省事。

具體建議設定（`app/layout.tsx`）：

```typescript
import { Inter, Noto_Sans_TC } from "next/font/google"

const inter = Inter({ subsets: ["latin"], variable: "--font-sans" })

const notoSansTC = Noto_Sans_TC({
  weight: ["400", "500", "700"], // 只取實際會用到的 3 檔，CJK 字集龐大，字重數量直接影響檔案大小
  variable: "--font-noto-tc",
  preload: true,
  display: "swap",
})
```

```html
<body className={cn("min-h-screen font-sans antialiased", inter.variable, notoSansTC.variable)}>
```

`app/globals.css` 的字型堆疊改為明確可驗證的內容，取代目前形同虛設的 `"LXGW WenKai", "Noto Sans TC"` 字串：

```css
body {
  font-family: var(--font-noto-tc), var(--font-sans),
    -apple-system, BlinkMacSystemFont,
    "PingFang TC", "Microsoft JhengHei", "Segoe UI",
    system-ui, sans-serif;
}
```

補充：
- CJK 字型在 `next/font/google` 通常沒有像拉丁字型那樣細分的 `subsets`（例如 `latin`/`latin-ext`）可選，控制檔案大小主要靠**限制字重數量**（只取 400/500/700，不要整組 100-900 都拉），務必在 `npm run build` 後實測 `.next/static/media` 底下產生的字型檔大小。
- Noto Sans TC 本身已包含設計協調的拉丁字符與數字，一般不需要再混搭其他西文字體；金額與表格數字統一套用 B7 的 `tabular-nums` 即可,不需要為了數字另外載入第二套字體（混搭西文字體反而容易在中西文交界處出現基線、字重不一致的違和感）。
- fallback 堆疊明確列出 Windows（微軟正黑體）與 Mac/iOS（蘋方）的系統字體名稱，讓 webfont 載入前後的畫面盡量一致，也讓極端情況（webfont 載入失敗）有一個體面的降級，而不是丟給瀏覽器猜。
- 不建議把裝飾性/手寫體（例如 `LXGW WenKai` 這類手寫楷體）當作介面主字體：手寫感字體會犧牲可辨識度，尤其在小字級的表格數字/中文字上；如果要用，僅限首頁品牌識別用的大字級標題，且必須真的自託管載入（而非只寫在 CSS fallback 字串裡卻沒有對應的字型檔），並自行確認授權允許商用/散布。
